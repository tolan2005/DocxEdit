## 2. Разрыв с мейнстрим-редакторами (приоритет владельца)

Отсортировано по «заметность для ежедневной работы ÷ трудозатраты».

### 2.1. Рендер многоколоночной вёрстки (Word)
`w:cols` сохраняется passthrough'ом (v1.5.4), но редактор показывает одну
колонку. **Рекомендация:** TextKit 1 умеет многоколоночную вёрстку нативно
(`NSTextContainer` + `NSLayoutManager.usesHyphenation`… фактически —
`NSTextContainer.widthTracksTextView` + несколько контейнеров), но у нас один
контейнер с пагинацией-подходом №1. Реалистичный путь: рисовать колонки в
`DocxTextView.drawBackground` как визуальный ориентир (линии разреза) — дёшево;
настоящая многоколоночная раскладка текста — большой проект (несколько
контейнеров в пагинации). **Начать с визуального ориентира.**

### 2.2. Вертикальный текст в ячейках (рендер)
`w:textDirection` round-trip есть (v1.5.17), рендер горизонтальный. Word
рисует повёрнутый текст. **Рекомендация:** в TextKit 1 вертикальный текст в
ячейке таблицы не выражается; честный вариант — рисовать текст ячейки
повёрнутым через `drawBackground` нельзя (текст в потоке). Оставить как есть с
отметкой в отчёте об открытии (уже сделано) — **не рекомендую тратить время**,
пока не появится TextKit 2-путь.

### 2.3. Живой TOC в панели навигации + drag-reorder разделов
Навигатор (v1.5.11) уже показывает H1–H6. У Word/Google Docs: клик правой —
«понизить/повысить уровень», drag — перестановка разделов. **Рекомендация:**
добавить контекстное меню в навигаторе (повысить/понизить заголовок — это
дёшево через `applyParagraphStyle`) и выделение текущего раздела при
прокрутке. Drag-reorder разделов — средний проект (перестановка блоков модели
+ пересборка storage одним undo-шагом — паттерн есть).

### 2.4. Typora-фички для MD source-режима
- **Живой рендер по месту** (Typora hybrid): заголовок сразу становится крупным
  при выходе курсора из строки. У нас WYSIWYG/source — два раздельных режима.
  Гибрид — большой проект; **не рекомендую** сейчас.
- Дёшево и полезно: **автопродолжение списков в source-режиме** (Enter в
  пункте `- x` вставляет `- `), **Tab/Shift+Tab — вложенность списка** в
  source-режиме, **⌘B/⌘I в source-режиме** оборачивают выделение в `**…**`.
  Все три — маленькие правки `MarkdownSourceView.Coordinator`.

### 2.5. Печать/PDF как в Word (колонтитулы, поля, водяные знаки)
Печать уже идёт через `NSPrintOperation` с настоящей пагинацией, но рисует ли
она листы/колонтитулы/водяные знаки так же, как `drawBackground`? Проверить
`knowsPageRange`/`rectForPage` у DocxTextView — если печать использует тот же
drawBackground, всё уже есть. **Действие: ручная проверка ⌘P на
многостраничном документе с водяным знаком** (30 минут, может закрыть вопрос).

### 2.6. Сравнение версий документов (Word: Compare/Combine)
Для личного инструмента редко нужно. **Отложить.**

### 2.7. Шифрование/пароль на документ (Word: password protect)
OOXML поддерживает (agile encryption). Для личного инструмента — редко.
**Отложить.**

### 2.8. Проверка орфографии и грамматики «как в Word»
Базовый NSSpellChecker подключён. У Word: красное/синее подчёркивание прямо в
тексте. Проверить, рисуются ли у нас волнистые подчёркивания `NSSpellChecker`
в TextKit 1 (должны нативно). Если нет — включить `continuousSpellChecking` /
`grammarChecking` на DocxTextView. **Действие: проверка + 1 строка кода.**

## 3. Технический долг (найдено аудитом)

### 3.1. Монолиты (главный архитектурный риск)
- `DocxIO.swift` — **3862 строки**: парсер тела, парсер стилей, парсер
  numbering, парсер колонтитулов, парсер rels, writer, рендер всех частей.
- `DocumentController.swift` — **3720 строки, 28 MARK-секций**; конвенция
  «движки-компаньоны» (R06) остановила рост лишь частично. Найден **дублирующийся
  MARK «Правописание и замены» (строки 125 и 1516)** — признак того, что код
  размножался копированием.
- `DocumentWindowView.swift` — 2875 строк: главный вид + ribbon-кнопки +
  DocxTextView + PaginatedTextContainer + DocxLayoutManager + FloatingImageNSView.

**Рекомендация (безопасный план, по шагам):**
1. Разрезать **по файлам без изменения кода**: DocxIO → `DocxIOParser.swift`,
   `DocxIOWriter.swift`, `DocxStylesParser.swift`, `NumberingXmlParser.swift`,
   `HFPartsParser.swift` (extension'ы того же класса/структур — нулевой риск).
2. DocumentController → extension-файлы по доменам: `+Tables.swift`,
   `+Images.swift`, `+Search.swift`, `+Footnotes.swift`, `+Spelling.swift`…
3. Только потом выделять новые движки-компаньоны по образцу CommentsEngine.
Эффект: навигация, merge-конфликты, ревью — без поведенческих изменений.

### 3.2. Инфраструктура кода
- **swiftlint + swiftformat**: 0 нарушений force-unwrap/try!/print — код уже
  дисциплинированный, линт закрепит. Установить через brew, конфиг с мягким
  набором правил, гонять в release.sh шагом (быстрый).
- **xcodeproj**: отсутствует — из-за этого нет XCUITest, Instruments-профилей
  и Address Sanitizer схем. Генерировать через **XcodeGen** из Package.swift
  (декларативно, коммитится yml) — откроет дорогу UI-тестам позже.

### 3.3. Тесты — пробелы
- **UI-слой не тестируется вообще** (RibbonView, диалоги, статусбар) —
  snapshot-тесты покрывают только мост. XcodeGen (см. выше) → XCUITest.
- **Производительность нет регрессионных тестов**: добавить
  `measure { }`-тесты на импорт/экспорт корпуса (21–24.docx) — поймает
  деградации вроде O(n²)-проходов подсветки.
- **Fuzz-покрытие**: DocxFuzzTests есть; добавить fuzz на **MD-импорт**
  (swift-markdown может паниковать на экзотике? — проверить) и на **битые
  numbering.xml/styles.xml**.
- Мелочь: захардкоженный PNG-фикстура повторяется в 3 тест-файлах — вынести в
  общий хелпер `TestImages.tinyPng`.

### 3.4. CI-квирки (известные, задокументированы)
- push-триггер не срабатывает на приватном репо (обход: dispatch/schedule) —
  периодически перепроверять; возможно, поможет пересоздание webhook'а через
  поддержку GitHub или переключение репо в публичный (если когда-нибудь
  решите открыть исходники).
- **Ротация релизов удалила промежуточные v1.5.11–v1.5.18** (искажённый
  createdAt). Артефакты целы локально в `build/`. **Рекомендация:** либо
  восстановить их (publish-github.sh для каждой версии), либо принять
  политику «окно 6 релизов» осознанно. Также `--latest` флаг у нового релиза
  приходилось выставлять вручную — добавить `gh release edit --latest` в
  publish-github.sh.

### 3.5. Надёжность данных
- **Autorecover не покрывает MD source-режим**: в source-режиме модель
  синкается best-effort, но если swift-markdown упал на недописанном
  синтаксисе, автосейв сохранит предыдущую модель, а не текст. Редкий, но
  коварный случай потери правок. **Рекомендация:** в autorecover при
  `isMarkdownSourceMode` сохранять `markdownSource` рядом с JSON модели
  (отдельный файл) и предлагать его при восстановлении.
- **`replaceModel` (v1.6.0) сбрасывает preservedParts/endnotes?** — проверено:
  переносит только metadata/pageSettings/styles/headerFooter/yamlFrontMatter.
  Если в MD-режиме править исходник, preserved-части DOCX-прошлого (до
  переключения в MD) теряются — но это осознанно (MD не хранит их). ОК.
- **Отсутствие валидации при открытии битых файлов**: XMLParser молча
  обрывает парсинг на синтаксической ошибке — пользователь видит обрезанный
  документ без предупреждения. **Рекомендация:** `parser.parserError` после
  `parse()` → запись в ImportReport («документ прочитан частично, ошибка XML
  на позиции N») — маленькое изменение, большая ценность.

## 4. Мелкие находки (быстрые победы)

1. **Дублирующийся MARK** «Правописание и замены» в DocumentController (125/1516)
   — проверить на дублирование логики, удалить/переименовать.
2. **⌘/ конфликт**: системный macOS «Show Help menu» (⌘/ не занят, но
   ⌘? = Help). Наш ⌘/ для source-режима ок, но проверить на RU-раскладке —
   `/` на ЙЦУКЕН это физическая клавиша с другим символом; монитор по keyCode
   (47) покроет — **убедиться, что ⌘/ попал в универсальный монитор v1.5.13**.
   Сейчас его там нет — добавить.
3. **`screencapture`/AppleScript UI-автоматизация** недоступны без
   Accessibility-разрешения — если захотите полноценные UI-тесты через
   AppleScript, выдайте разрешение Терминалу (Системные настройки →
   Конфиденциальность → Универсальный доступ).
4. **README публичного репо** (67 строк) не отражает текущее состояние
   (source-режим, водяные знаки, endnotes…). Обновить — это «витрина».
5. **AboutReleaseNotes.recent** — ручное ведение, уже дважды забывалось
   (ADR-027 п.1). release.sh проверяет наличие записи, но не её содержание.
   Оставить как есть (проверка есть), но помнить.
6. **`testOutput.log`/`test-output.log`** в .gitignore упомянут только в
   одной форме — унифицировать.

## 6. Что НЕ рекомендую делать
- **TextKit 2 миграция** — сломает списки (двойные маркеры) и непечатаемые
  символы; решено в ADR-027/034, выгоды для личного инструмента сомнительны.
- **Accessibility (VoiceOver)** — 0% покрытия; ценно для публичного продукта,
  для личного — не приоритет.
- **Локализация EN интерфейса** — инфраструктура есть (R09), но строки
  захардкожены по-русски в 140+ местах; вычищать стоит только перед
  публичным EN-запуском.
- **Микро-оптимизации производительности** — 2.5 с полный тест-прогон,
  34 с release-сборка: узких мест не видно без профилирования реального
  использования; сначала Instruments (нужен xcodeproj, см. §3.2).
