# REQUIREMENTS — Публикация релизов на GitHub и автообновление

> Документ описывает функциональные и нефункциональные требования к двум связанным задачам DocxEdit:
> (1) публикация артефактов релиза на GitHub Releases с автоматической чисткой старых;
> (2) встроенный механизм автоматической проверки/установки обновлений в самом приложении.
>
> Статус: **проект требований**. Дата: 2026-07-16. Автор: DocxEdit maintainer.
>
> **Целевой репозиторий:** <https://github.com/tolan2005/DocxEdit> (public).
> Owner: `tolan2005`, repo: `DocxEdit`. Публичный доступ — обновления скачиваются без токенов; ротация освобождает место в ленте релизов, историческую целостность SHA256 обеспечивает `SHA256SUMS.history` (см. §8 R4).

## 1. Обзор и мотивация

Сейчас релизы DocxEdit собираются локально скриптом `scripts/release.sh` и складываются в `build/vX.Y.Z/`. Дистрибуция за пределы машины разработчика не автоматизирована; пользователь узнаёт о новых версиях только вручную. Задача — закрыть весь цикл «собрал → выложил → пользователь получил обновление» без ручных шагов после `release.sh`.

### 1.1 Цели

- **G1.** Артефакты релиза (`.dmg`, `.app.zip`, `SHA256SUMS`) публикуются на GitHub Releases автоматически при выпуске.
- **G2.** На GitHub видимо только N последних релизов (по умолчанию **N=3**); более старые релизы удаляются (артефакты и, опционально, git-теги остаются).
- **G3.** Установленное приложение самостоятельно проверяет наличие новой версии и предлагает пользователю обновиться в один клик.
- **G4.** Приватность по умолчанию (ADR-008): проверка обновлений опциональна, без телеметрии, без сбора идентификаторов.

### 1.2 Нецели (v1 автообновления)

- Дельта-обновления/патчи — только полная замена бандла.
- Sparkle framework как зависимость — реализуем **свою минимальную схему** (см. §5.3 «Альтернативы»).
- Автоматическая тихая установка без согласия пользователя.
- Beta-каналы/rollout по проценту пользователей (задел на будущее в §7).

## 2. Область действия

### 2.1 Что затрагивает

- `scripts/release.sh` — шаг публикации на GitHub.
- `scripts/publish-github.sh` (новый) — обёртка над `gh release`.
- `Sources/DocxEdit/Sources/Updater/` (новый каталог) — движок автообновления.
- `Sources/DocxEdit/Sources/AppPreferences.swift` — настройка «Проверять обновления».
- `Sources/DocxEdit/Sources/PreferencesView.swift` — UI настройки.
- `Sources/DocxEdit/Sources/DocxEditApp.swift` — пункт меню «Проверить обновления…», регистрация observer для периодической проверки.
- `CLAUDE.md` — новая секция про updater; ADR-XXX; §6 фичи; §8 ключевые файлы.

### 2.2 Что НЕ затрагивает

- Модель документа, DOCX I/O, ribbon, редактор — без изменений.
- Существующие тесты — updater покрывается собственными тестами, не ломает 204 существующих.

## 3. Функциональные требования — часть A: публикация на GitHub

### 3.1 GitHub Release при выпуске

- **F-A-1.** `release.sh` после успешной локальной сборки и обновления `CLAUDE.md`/`CHANGELOG.md` вызывает `scripts/publish-github.sh <version>`.
- **F-A-2.** `publish-github.sh` создаёт GitHub Release с тегом `vX.Y.Z`, названием «vX.Y.Z — <codename>» и телом из соответствующей секции `CHANGELOG.md` (извлечение по заголовку `## vX.Y.Z` до следующего `## v`).
- **F-A-3.** К релизу прикрепляются файлы из `build/vX.Y.Z/`:
  - `DocxEdit-X.Y.Z.dmg`
  - `DocxEdit-X.Y.Z.app.zip`
  - `SHA256SUMS`
- **F-A-4.** Pre-release (`X.Y.Z` с `-rc.*`, `-beta.*`, `-alpha.*` в тегe) публикуется с флагом `--prerelease`.
- **F-A-5.** Инструмент — `gh` CLI (GitHub CLI); авторизация через `gh auth login` заранее, скрипт делает `gh auth status` и падает с понятным сообщением, если не авторизован.

### 3.2 Ротация — только N последних релизов

- **F-A-6.** После успешной публикации `publish-github.sh` вызывает **ротацию**: получает список релизов (`gh release list --limit 100 --json tagName,createdAt,isDraft,isPrerelease`), сортирует по дате убывания.
- **F-A-7.** Для релизов **за пределами топ-N** (по умолчанию N=3, задаётся переменной `KEEP_RELEASES` в env, диапазон 1–20):
  - Удаляется **GitHub Release** (`gh release delete <tag> --yes`).
  - **Не удаляется** git-тег (`--cleanup-tag` не передаётся) — историю на GitHub сохраняем, чтобы можно было вручную повторно создать релиз при необходимости.
- **F-A-8.** Draft-релизы (`isDraft=true`) в подсчёт топ-N не входят и не удаляются.
- **F-A-9.** Pre-release в подсчёте участвуют наравне со стабильными (иначе pre-release с рабочим артефактом мог бы вытеснить стабильный из ленты обновлений). Отдельный лимит для pre-release — задел R+1 (не в v1).

### 3.3 Идемпотентность и восстановление

- **F-A-10.** Если релиз с таким тегом уже существует на GitHub, скрипт **обновляет** артефакты (`gh release upload <tag> <files> --clobber`), не создаёт дубль. Это позволяет перевыпустить артефакт после исправления DMG без bump версии.
- **F-A-11.** Если создание/обновление на GitHub упало — локальные артефакты в `build/vX.Y.Z/` остаются нетронутыми; `CLAUDE.md`/`CHANGELOG.md` уже обновлены (это в `release.sh` идёт до `publish-github.sh`); ротация НЕ выполняется. Скрипт возвращает ненулевой код — `release.sh` выводит инструкцию как повторить: `./scripts/publish-github.sh X.Y.Z`.
- **F-A-12.** Ротация — отдельный этап после успешной публикации; её падение не откатывает публикацию, но выводится в stderr с чёткой пометкой и списком «что не удалилось».

### 3.4 Опциональность

- **F-A-13.** `release.sh` принимает флаг `--no-publish` — пропускает GitHub-шаг (для локальных тестовых сборок).
- **F-A-14.** Если репозиторий не имеет GitHub remote (`gh repo view` падает), `release.sh` **не падает**: выводит warning и пропускает публикацию (эквивалент `--no-publish`).

## 4. Функциональные требования — часть B: автообновление в приложении

### 4.1 Основной flow

- **F-B-1.** Приложение при запуске (после отрисовки главного окна, чтобы не блокировать splash) через `URLSession` дёргает GitHub API `GET https://api.github.com/repos/tolan2005/DocxEdit/releases/latest` и получает JSON с `tag_name`, `name`, `body`, `assets[]`. Owner/repo константы в `Sources/DocxEdit/Sources/Updater/UpdateConfig.swift` — на случай форка меняются в одном месте.
- **F-B-2.** Сравнивает `tag_name` (strip `v`) с текущей версией (`Bundle.main.object(forInfoDictionaryKey: "CFBundleShortVersionString")`) через semver. Если удалённая > текущей — показывает **ненавязчивое уведомление** (banner-style окно, не modal) с описанием и кнопками:
  - **«Установить сейчас»** — начинает загрузку.
  - **«Позже»** — закрывает banner, следующая проверка через настроенный интервал.
  - **«Пропустить эту версию»** — сохраняет `skippedVersion: X.Y.Z` в `AppPreferences`; версия не предлагается снова, пока не выйдет ещё более новая.
- **F-B-3.** Из `assets[]` берётся `.dmg` (или `.app.zip` как fallback) — предпочтение `.dmg` для нативного UX. Асеты идентифицируются по расширению и совпадению с шаблоном `DocxEdit-<version>.<ext>`.
- **F-B-4.** Загрузка идёт через `URLSession.download` в temporary directory. Отображается прогресс в самом banner-окне.
- **F-B-5.** После загрузки — **обязательная проверка SHA256** против `SHA256SUMS` (тоже загружается из релиза). При несовпадении — ошибка, файлы удаляются, обновление отменяется, пользователю показывается «Не удалось проверить целостность файла — обновление отменено».
- **F-B-6.** При успешной проверке:
  - `.dmg` — открывается в Finder (`open path.dmg`), пользователь вручную перетаскивает в Applications. Показывается tooltip «Перетащите DocxEdit.app в папку Applications и перезапустите приложение».
  - `.app.zip` — распаковка + попытка in-place replace через helper-скрипт (см. §4.5).

### 4.2 Периодичность и настройки

- **F-B-7.** Интервал проверки в `AppPreferences`:
  - «При запуске» (по умолчанию)
  - «Раз в день»
  - «Раз в неделю»
  - «Никогда»
- **F-B-8.** Настройка на вкладке **«Основные»** в Preferences (существующая TabView в `PreferencesView.swift`).
- **F-B-9.** «Раз в день»/«Раз в неделю» — таймер, `Timer.scheduledTimer`, интервал сохраняется относительно `lastCheckDate` в UserDefaults. Проверка при запуске всегда происходит, если `lastCheckDate + interval < now`.
- **F-B-10.** Ручная проверка: пункт меню **DocxEdit → «Проверить обновления…»** — принудительно, независимо от настройки и `skippedVersion` (сбрасывает `skippedVersion` только если пользователь явно выбрал «Установить» — иначе оставляет).

### 4.3 Приватность и сеть

- **F-B-11.** **Никаких User-Agent-хвостов с идентификаторами машины**. User-Agent: `DocxEdit/<version> (macOS)`, ничего больше. Никаких cookies, никаких UUID.
- **F-B-12.** Запросы идут напрямую к `api.github.com` и `github.com` (для скачивания assets). Никаких промежуточных сервисов Anthropic/автора.
- **F-B-13.** При настройке «Никогда» — **никаких** сетевых запросов инициируется приложением автоматически (кроме явного клика «Проверить обновления…»).
- **F-B-14.** Timeout URL-запросов — 15 сек на metadata, 5 мин на download. При таймауте — silent skip (не спамим уведомлениями), лог в консоль.

### 4.4 Обработка ошибок

- **F-B-15.** Нет сети / DNS-фейл / api.github.com недоступен / rate-limit (403) — тихо игнорируем при автоматической проверке; при ручной — показываем «Не удалось проверить обновления: <причина>. Повторите позже.»
- **F-B-16.** Malformed JSON от GitHub — тихий пропуск + лог, не падаем.
- **F-B-17.** Rate-limit GitHub API — публичный endpoint даёт 60 запросов/час на IP без токена; для DocxEdit этого хватает с запасом (проверка раз в день). Никаких токенов в клиенте.
- **F-B-18.** Отсутствие подходящего asset (нет `.dmg` в relase) — показываем «Обновление доступно, но артефакт не найден. Скачайте вручную: <ссылка>».

### 4.5 In-place replace (для `.app.zip`)

- **F-B-19.** Helper-скрипт `Scripts/apply-update.sh` (вложен в bundle `Resources/`), вызывается через `Process`:
  - Ждёт завершения текущего процесса (`--wait <pid>`).
  - Удаляет старый `.app` из `/Applications` (или откуда запущен).
  - Распаковывает `.app.zip` на его место.
  - Запускает новый `.app` (`open`).
- **F-B-20.** Приложение перед вызовом скрипта: закрывает все окна с проверкой несохранённых изменений (используем существующий `WindowCloseGuard`), потом `NSApp.terminate(nil)` **не вызываем** — вместо этого запускаем скрипт как detached, он ждёт наш PID, и мы штатно завершаемся через `NSApp.terminate(nil)`.
- **F-B-21.** Права: если приложение установлено в `/Applications` и не принадлежит текущему пользователю (например, установлено под sudo), заменить без запроса пароля не получится. В этом случае — fallback на `.dmg`-flow (открыть DMG, показать инструкцию).

### 4.6 UI компоненты (новые)

- **F-B-22.** `UpdateNotificationView` — SwiftUI View, показывается в отдельном `NSWindow` (по паттерну ADR-039 п.7: `NSWindow(contentRect:) + NSHostingView(sizingOptions: [])` — единственный разрешённый паттерн диалогов после краха ADR-039).
- **F-B-23.** Ширина 480×320, заголовок «Доступно обновление: vX.Y.Z», секция с release notes (scrollable Text из `body`), кнопки «Установить»/«Позже»/«Пропустить».
- **F-B-24.** При загрузке — прогресс-бар и «Отмена».

## 5. Технические решения

### 5.1 Semver-сравнение

Использовать простой встроенный компаратор — `X.Y.Z` разбить на `Int`, сравнить лексикографически. Pre-release суффиксы (`-rc.1`) v1 не поддерживаем (пре-релизы GitHub включены в ротацию, но для сравнения версий парсим только X.Y.Z, суффикс игнорируем; это означает, что после `1.1.0-rc.1` мы НЕ покажем `1.1.0` как обновление — задел на v2, см. §7).

### 5.2 Хранение состояния

`AppPreferences.swift`:
```swift
var updateCheckFrequency: UpdateFrequency  // .onLaunch | .daily | .weekly | .never
var lastUpdateCheck: Date?
var skippedVersion: String?
```

### 5.3 Почему не Sparkle

Sparkle — стандарт де-факто для macOS-автообновлений, но:
- Требует Ed25519-подпись каждого релиза + распространение публичного ключа (сложность для freeware-проекта).
- Собственная зависимость (Cocoapod/SPM) — увеличивает bundle.
- Использует свой формат appcast (XML) — нужен отдельный статический хост.
- Для нашего масштаба (проверка раз в день против GitHub API) избыточно.

Наша схема проще: полагаемся на HTTPS + SHA256SUMS (тоже подписан позже через notary-подпись бандла v1.0.1+).

### 5.4 Тесты

- **Unit-тесты**:
  - `SemverComparatorTests` — 12 кейсов (равные, older, newer, pre-release игнор).
  - `GitHubReleaseParserTests` — парсинг фиктивного JSON (fixture в `Tests/UpdaterTests/Fixtures/`).
  - `SHA256VerifierTests` — валидный/невалидный чек-сум, отсутствующая строка.
- **Интеграционных тестов сети — нет** (моки на URLSession через protocol injection `URLSessionProtocol`).
- Snapshot-тест `UpdateNotificationView` в light/dark режимах — по паттерну `BridgeSnapshotTests`.

### 5.5 Info.plist изменения

- `NSAppTransportSecurity` — не трогаем, `api.github.com` и `github.com` идут по HTTPS с валидными сертификатами.
- Никаких новых entitlements.

## 6. Приемочные критерии

### 6.1 Часть A (GitHub publishing)

- [ ] `./scripts/release.sh 1.0.1 "Test"` создаёт GitHub Release с 3 asset'ами, тело релиза = соответствующая секция CHANGELOG.
- [ ] После 4-го релиза (при `KEEP_RELEASES=3`) первый исчезает из ленты релизов, но git-тег остаётся.
- [ ] `./scripts/release.sh 1.0.1 "Test" --no-publish` не трогает GitHub.
- [ ] Повторный запуск релиза с той же версией обновляет asset'ы, не создаёт дубль.
- [ ] Отсутствие `gh` CLI даёт понятную ошибку с ссылкой на установку.

### 6.2 Часть B (in-app updater)

- [ ] Приложение при запуске (с настройкой «При запуске») дёргает `api.github.com` один раз; при настройке «Никогда» — не дёргает вовсе (проверено через network sniffer).
- [ ] Пункт меню «Проверить обновления…» всегда работает.
- [ ] Более новая версия показывает banner; «Пропустить эту версию» больше не показывает её до выхода ещё более новой.
- [ ] SHA256-верификация: подмена скачанного файла даёт ошибку целостности, обновление отменяется.
- [ ] Загрузка `.dmg` открывается в Finder; `.app.zip` заменяет бандл через helper-скрипт (проверить в собранной сборке `/Applications/DocxEdit.app`).
- [ ] Rate-limit/offline не крашит приложение и не показывает алертов при автоматической проверке.
- [ ] UI-диалог использует паттерн `NSWindow(contentRect:) + NSHostingView(sizingOptions: [])` (ADR-039 п.7).

## 7. Задел на будущее (v2+ автообновления)

- **Beta-канал**: настройка «Тестовые сборки» → в API-запросе брать `releases` (не `releases/latest`) и брать первый `isPrerelease=true`.
- **Delta-обновления**: bsdiff между версиями, публикация `.dmg` + `.delta` в assets.
- **Подпись метаданных**: Ed25519 подпись `SHA256SUMS` — защита от MITM даже при компрометации GitHub.
- **Pre-release semver-сравнение**: `1.1.0-rc.1 < 1.1.0`.
- **Отдельный лимит** для pre-release в ротации (например: топ-3 stable + топ-2 pre-release).
- **Опциональная тихая установка** (для регулярных пользователей): чекбокс «Устанавливать обновления автоматически».

## 8. Риски и открытые вопросы

- **R1.** Notarization обязательна для in-place replace без Gatekeeper-варнинга у пользователя. Пока v1.0.0 подписан ad-hoc — автообновление в v1 будет показывать Gatekeeper-варнинг при первом запуске новой версии. **Решение**: закрыть Developer ID + нотаризация (post-1.0 задача) **до** релиза этого функционала.
- **R2.** GitHub API rate-limit без токена — 60/час/IP для публичных репозиториев (репо `tolan2005/DocxEdit` — public, токен клиенту не нужен). При кластерном NAT (корп. сеть с 1 IP на 100 пользователей) лимит может выстрелить. **Митигация**: cache metadata в UserDefaults на 1 час — не долбим API повторно в пределах часа даже при перезапуске.
- **R3.** `apply-update.sh` — root-privileged path (если `/Applications` защищён). **Митигация**: fallback на `.dmg` UX + сообщение пользователю.
- **R4.** Удаление старого релиза с GitHub теряет исторические `SHA256SUMS` — если у пользователя старая версия и он хочет проверить целостность, файлов нет. **Митигация**: `SHA256SUMS` всех релизов дублируется в отдельный файл `SHA256SUMS.history` в репозитории (append-only).
- **Q1.** Сохранять ли `.pdf`-экспорт release notes в assets релиза? — **Нет в v1**, только `.dmg`/`.zip`/`SHA256SUMS`.
- **Q2.** Показывать ли пользователю changelog **всех** пропущенных версий (не только следующей)? — **Да**: в banner собирать `body` всех релизов от текущей+1 до latest, сцеплять с разделителями.

## 9. План реализации (черновой)

Разбиваю на релизы по конвенции проекта (один релиз = одна фича):

1. **v1.1.0** — Часть A (GitHub publishing + ротация). Функция «продвинутая» — сразу minor bump, потому что открывает публичное распространение.
2. **v1.2.0** — Часть B (auto-updater движок, UI, настройки). Требует v1.1.0 как источник артефактов, потому идёт после.
3. **v1.2.1..N** — точечные фиксы UX по фидбеку.
4. **v1.3.0** — задел из §7 (beta-канал/delta) — уже после публичного использования.
