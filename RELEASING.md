# RELEASING.md — рабочий процесс «приватный код + публичные релизы»

> Шаблон для проектов, где исходный код живёт в **приватном** репозитории
> (с CI), а пользователи получают готовые артефакты из **публичного**
> репозитория — без публикации кода. Отлажено на macOS-приложении (Swift,
> DMG-релизы), применимо к любому проекту с бинарными артефактами.
>
> Дата: 2026-08-24. Везде ниже: `<PROJ>` — имя проекта, `<OWNER>` — владелец
> GitHub, `<PUB>` — публичный репо (релизы), `<PRIV>` — приватный репо (код).

---

## 1. Модель: два репозитория

| Репозиторий | Видимость | Содержимое | Назначение |
|---|---|---|---|
| `<OWNER>/<PROJ>` (`<PUB>`) | **public** | README.md, LICENSE, GitHub Releases | Витрина + раздача DMG/zip пользователям + точка для in-app updater |
| `<OWNER>/<PROJ>-src` (`<PRIV>`) | **private** | Полный исходник, тесты, скрипты, CI | Рабочее место разработки |

Зачем разделять: код не публикуется, но у пользователей остаётся обычный
GitHub-опыт (Releases, badges, issue-трекер по желанию), а у разработчика —
обычный GitHub-опыт с CI и историей.

**Правила:**
- В `<PUB>` — только README/LICENSE/.gitignore (whitelist). НИКОГДА не пушить
  туда ветки и теги с кодом.
- В `<PRIV>` — всё. CI живёт там.
- GitHub Release в `<PUB>` создаётся тегом на README-ветке (`--target`), т.к.
  локальные теги ссылаются на коммиты с кодом, которых в `<PUB>` нет.

## 2. Локальная git-настройка

```
origin  →  https://github.com/<OWNER>/<PROJ>.git      (публичный, релизы)
src     →  https://github.com/<OWNER>/<PROJ>-src.git  (приватный, код)
```

- `git push` по умолчанию — в `src` (upstream main = src/main).
- В `origin` ничего не пушим вручную; туда ходит только `gh release`.
- Если в проекте когда-то стоял «whitelist-.gitignore» (публиковался только
  README), при включении кода в git его надо **переписать на обычный** — иначе
  исходники молча не попадут в историю.

## 3. CI (в приватном репо)

`.github/workflows/ci.yml`: macOS-раннер, `swift build -c release` + `swift test`.

- Триггеры: `push`, `pull_request`, `workflow_dispatch`, `schedule`
  (еженедельный cron — страховка).
- ⚠️ **Квирк:** на свежесозданном приватном репо GitHub может не регистрировать
  push-события для Actions (наблюдалось 2026-08). Обход: `workflow_dispatch` +
  расписание; при необходимости — `gh workflow run <NAME> --repo <OWNER>/<PROJ>-src`.
- CI на чистом раннере ловит переносимость компилятора (нам — баг
  Swift 5.10 vs локальный Swift 6.3 в первый же прогон).

## 4. Релизный пайплайн (release.sh)

Одна команда: `./scripts/release.sh <VERSION> "<CODENAME>" "" "<CHANGES>"`

Шаги (порядок важен):
1. **Гейт About/чейнджлога**: выпускаемая версия должна иметь запись в списке
   «что нового» в About-окне приложения (иначе пользователь не увидит релиз).
2. **Тесты**: `swift test` (полный сьют; красный тест = релиза нет).
   Если установлен — `swiftlint` (graceful skip, если нет).
3. **Сборка**: build.sh → `.app` + smoke-тест бандла (Info.plist через plutil,
   Mach-O через lipo, версия) → `.app.zip` + `.dmg` + `SHA256SUMS` в
   `build/v<VERSION>/`.
4. **UI-смоук** (опционально, `SKIP_UI_SMOKE=1` отключает): открытие корпусных
   документов живым `.app` без краша (процесс жив + нет новых crash-reports).
5. **Документация**: CHANGELOG.md и память проекта обновляются скриптами
   (автогенерация секции релиза).
6. **Тег**: `git tag -a v<VERSION>` локально, push **в `src`** (НЕ в `origin` —
   тег утянул бы историю с кодом в публичный репо!).
7. **Публикация**: scripts/publish-github.sh — создаёт GitHub Release в
   `<PUB>` с DMG+zip+SHA256SUMS.

## 5. publish-github.sh — ключевые детали

- Инструмент — `gh` CLI (`gh auth login` один раз). Не curl+PAT (токены) и не
  Actions (не нужен CI-раннер для локальных сборок).
- Создание релиза: `gh release create <TAG> <files> --target <origin/main-sha>`
  — тег создаётся на README-коммите публичного репо, потому что локальный тег
  содержит код, которого в `<PUB>` нет. `--target` применяется только если
  тега нет в `<PUB>`.
- Идемпотентность: существующий релиз → `gh release upload --clobber` +
  `gh release edit` (перевыпуск артефакта без bump версии).
- **`--latest` всегда выставляется явно** (`gh release edit --latest`), т.к.
  GitHub помечает Latest по `createdAt`, а у target-тегов она искажена
  (см. §7, урок 2).
- **Ротация по semver, не по createdAt** (см. §7, урок 2):
  `gh release list --json tagName,isDraft` → `sort -Vr` → всё за пределами
  топ-`KEEP` удаляется (`gh release delete --yes` БЕЗ `--cleanup-tag` — git-теги
  остаются архивом). Текущий тег исключён из ротации всегда.
- Отсутствие `gh`/remote/сети — graceful skip с инструкцией «повторить
  вручную», не падение релиза.

## 6. Типичные команды

```
# Полный релиз (тесты → сборка → smoke → тег → публикация):
./scripts/release.sh 1.7.0 "Codename" "" "Описание изменений"

# Перепубликация артефактов без новой версии:
./scripts/publish-github.sh 1.7.0

# Прогон CI вручную:
gh workflow run CI --repo <OWNER>/<PROJ>-src

# Посмотреть CI:
gh run list --repo <OWNER>/<PROJ>-src

# Восстановить удалённый релиз (артефакты в build/vX.Y.Z/):
KEEP_RELEASES=20 ./scripts/publish-github.sh X.Y.Z
```

## 7. Извлечённые уроки (профилактика инцидентов)

1. **git checkout -- <папка> может снести незакоммиченную работу.** У нас
   откатил правки двух релизов, потому что релизный скрипт коммитит только
   документацию, а код оставался в рабочем дереве. Профилактика:
   **коммитить код ДО release.sh**, либо включить шаг «код закоммичен?» в
   релизный гейт. (release.sh гоняет тесты по рабочему дереву, но тег/публикация
   опираются на git-историю — рассинхрон гарантирован.)
2. **У GitHub Releases искажённый `createdAt` у релизов, созданных через
   `--target` на старый коммит** — createdAt ≈ дата README-коммита, не дата
   публикации. Ротация по createdAt дважды снесла свежие релизы (v1.5.11,
   v1.6.2). Профилактика: ротация по semver + исключение текущего тега +
   явный `--latest` после create.
3. **push-триггер Actions на свежем приватном репо может молчать.**
   Профилактика: `workflow_dispatch` + еженедельный `schedule` как страховка;
   проверять `gh run list` после первого push'а.
4. **Пуш релизного тега в публичный репо публикует историю кода.** Тег
   ссылается на коммит с исходниками; `git push origin v1.x` утянет всю цепочку
   в `<PUB>`. Профилактика: release.sh пушит теги только в `src`; publish
   использует `--target`.
5. **Snapshot-эталоны и размеры шрифтов могут «съезжать» между машинами** —
   perceptualPrecision ~0.98, а не 1.0.
6. **Автогенерация «About»-записей забывается** — гейт в release.sh (шаг 1)
   ловит это дешевле, чем жалоба пользователя.
7. **Приватный репо + Actions: macOS-раннеры жгут минуты с коэффициентом 10**
   (2000 мин/мес → ~200 минут macOS). Релизы локальные; CI — только тесты,
   поэтому минут хватает с запасом. Не ставить на CI сборку DMG.

## 8. Что нужно, чтобы применить это в новом проекте

1. Создать два репо: `<PROJ>` (public, README+LICENSE) и `<PROJ>-src` (private).
2. Скопировать: `scripts/release.sh`, `scripts/build.sh`,
   `scripts/publish-github.sh`, `scripts/ui-smoke.sh` (macOS-приложения),
   `scripts/update-changelog.sh`, `.github/workflows/ci.yml`, `.swiftlint.yml`.
3. Заменить `<PROJ>`-плейсхолдеры (имя бандла, имя репо, путь fixtures).
4. В проекте: конвенция «AboutReleaseNotes.recent» или её аналог
   (гейт «что нового»), папка `Tests/…/Fixtures` с реальными файлами для смоука.
5. `gh auth login`; первый релиз — с ручной проверкой: тег в src, релиз в pub,
   Latest верный, DMG открывается.
